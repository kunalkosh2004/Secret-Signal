# Secret Signal --- Rooms & Real-Time Backend Progress

## Overview

This document summarizes the work completed so far for **Phase 1: Rooms
& Real-Time Connection** of the Secret Signal project.

The implemented backend now supports:

-   Creating rooms
-   Joining rooms
-   Leaving rooms
-   Persistent room membership in PostgreSQL
-   JWT-authenticated WebSocket connections
-   Room membership authorization for WebSockets
-   In-memory WebSocket connection management
-   Broadcasting authoritative `ROOM_STATE` events to connected room
    members
-   End-to-end manual testing with multiple users and simultaneous
    WebSocket clients

------------------------------------------------------------------------

# 1. Room Database Layer

## 1.1 Room model

Created:

``` text
app/rooms/models.py
```

The `Room` model contains:

-   `id`
-   `code`
-   `host_id`
-   `status`
-   `max_players`
-   `settings`
-   `created_at`

Important design decisions:

-   Room codes are unique and indexed.
-   `host_id` references `users.id`.
-   Room settings are stored as JSON.
-   Room status currently uses a string such as `waiting`.
-   Creation timestamps are generated by the database.

------------------------------------------------------------------------

## 1.2 RoomPlayer membership model

A `RoomPlayer` model was added to represent membership between users and
rooms.

Conceptually:

``` text
User
  ↓
RoomPlayer
  ↓
Room
```

The membership model contains:

-   `id`
-   `room_id`
-   `user_id`
-   `joined_at`

A unique constraint prevents duplicate membership:

``` text
(room_id, user_id) must be unique
```

This design was chosen instead of storing player IDs inside a JSON field
because room membership needs proper querying, constraints, joins, and
future room-specific state.

# 4. Room Service Layer

Created:

``` text
app/rooms/service.py
```

Implemented:

-   `create_room`
-   `join_room`
-   `leave_room`

## Room code generation

Room codes are generated using Python's `secrets` module with uppercase
letters and digits.

Example:

``` text
UCR6T0
```

Before creating a room, the service checks whether the generated code
already exists.

The database unique constraint remains the final integrity guard.

## create_room flow

``` text
Generate room code
        ↓
Check code uniqueness
        ↓
Create Room
        ↓
Add host as first RoomPlayer
        ↓
Return Room
```

## join_room rules

The service verifies:

1.  Room exists.
2.  Room status is `waiting`.
3.  User is not already a member.
4.  Room has available capacity.
5.  User membership is inserted.

## leave_room rules

The service verifies:

1.  Room exists.
2.  User is a member.
3.  Host is not using the normal leave operation.
4.  Membership is removed.

The current design prevents the host from leaving through the normal
leave operation until explicit host-transfer or room-closing rules are
implemented.

# 5. Room REST API

Created:

``` text
app/rooms/router.py
```

Registered the room router in:

``` text
app/main.py
```

Implemented endpoints:

## Create room

``` text
POST /api/v1/rooms
```

Requires JWT authentication.

The host ID comes from the authenticated user, not from the request
body.

## Join room

``` text
POST /api/v1/rooms/join
```

Request example:

``` json
{
  "code": "UCR6T0"
}
```

## Get room

``` text
GET /api/v1/rooms/{code}
```

Returns room metadata.

## Leave room

``` text
POST /api/v1/rooms/{code}/leave
```

Removes the authenticated user's membership if allowed by service rules.

## Current error mapping

The router currently maps service `ValueError` messages to HTTP
responses such as:

-   `404` --- room not found
-   `409` --- duplicate membership
-   `409` --- room full
-   `400` --- other invalid room operations

A future improvement is to replace string-based error mapping with typed
domain exceptions.

# 8. WebSocket Handlers

Created:

``` text
app/websocket/handlers.py
```

Implemented:

-   `authenticate_websocket`
-   `authorize_room_connection`
-   `handle_message`
-   `broadcast_room_state`

## Authentication

The WebSocket token is decoded using the existing JWT security logic.

Flow:

``` text
Token
  ↓
decode_access_token
  ↓
Read sub claim
  ↓
Convert to user ID
  ↓
Load User from PostgreSQL
```

## Authorization

A valid JWT alone is not enough to connect to a room.

The backend checks:

``` text
Does room exist?
        ↓
Is user a RoomPlayer member?
        ↓
Allow or reject connection
```

## Event handler skeleton

Incoming JSON messages are routed using the `type` field.

Current behavior:

-   Missing event type → `ERROR`
-   Unknown event type → `ERROR`

This is the foundation for future events such as:

-   `PLAYER_READY`
-   `SEND_MESSAGE`
-   `CAST_VOTE`
-   game-phase events

# 10. ROOM_STATE Broadcasting

Implemented authoritative room snapshots.

Example event:

``` json
{
  "type": "ROOM_STATE",
  "room": {
    "id": 1,
    "code": "UCR6T0",
    "host_id": 6,
    "status": "waiting",
    "max_players": 8,
    "settings": {}
  },
  "players": [
    {
      "id": 6,
      "username": "asd123kunal"
    }
  ]
}
```

The design separates two types of state:

## PostgreSQL state

Source of truth for:

-   room membership
-   room host
-   room status
-   room settings

## ConnectionManager state

Source of truth for:

-   currently connected WebSocket clients
-   broadcast delivery targets

A disconnected socket does not automatically remove the player from room
membership.

# Important Technical Improvements for Later

These are known improvements, not blockers for the current milestone:

## Transaction ownership

Currently repository write methods commit independently.

A future refactor should make multi-step workflows atomic:

``` text
BEGIN
  create room
  add host membership
COMMIT
```

and rollback the complete workflow if any step fails.

## Typed domain exceptions

Replace string matching on `ValueError` with exceptions such as:

``` text
RoomNotFoundError
RoomFullError
AlreadyInRoomError
HostCannotLeaveError
```

## WebSocket token transport

The development implementation sends the JWT in the WebSocket query
string.

A production design should consider:

-   short-lived WebSocket tickets
-   secure cookie-based authentication
-   an application-level authentication handshake

## Shorter database session lifetime

The current WebSocket endpoint keeps its database session around the
socket lifecycle.

A scalable version should use short-lived sessions for authentication
and individual event operations.

## Resilient broadcast cleanup

`broadcast_to_room()` should eventually catch failed socket sends and
remove stale connections without interrupting delivery to healthy
clients.

## Online presence

`ROOM_STATE.players` currently represents database membership, not live
connection presence.

A future event schema can include:

``` json
{
  "id": 6,
  "username": "asd123kunal",
  "is_connected": true
}
```
